# Context rot recedes but never vanishes

Nobody has published a measurement of Claude Code task success against how full the context window is, so the honest answer to "how badly does it degrade?" is a set of adjacent measurements, not one curve. Those measurements agree on direction: every model tested gets less reliable as input grows, and 2026 Claude models have pushed the point where this bites from tens of thousands of tokens out to several hundred thousand. On vendor-reported long-context reasoning tests, recent Claude models hold roughly 85-99% accuracy at 256K tokens and lose 12 to 45 points by 1M, with each generation losing less than the one before. Degradation tracks absolute token count and what the tokens contain (near-duplicates, stale tool output, superseded plans), not the percentage of the window used, so "stay under 40%" rules carried over from 200K windows have no experimental basis. In agentic coding the best-measured harm is not the full window itself but what compaction drops: about one in five user-stated constraints, and about one in three process or scope instructions, do not survive a Claude Code compaction summary. Claude Code now defaults to a 1M window with auto-compaction at about 967K tokens, and Anthropic's docs call aggressive context management outdated advice while its API docs still state that accuracy and recall degrade as token count grows. The largest gap in the evidence is the newest models: no degradation curve exists for Opus 5.5 or the Fable 5.x models from Anthropic or from independent testers.

## No one has measured Claude Code against its own fill level

The question as asked has no direct answer in the literature. No study found holds a coding task fixed and varies how full Claude Code's context is; there is no Anthropic telemetry, no third-party harness and no reproducible repository. What exists is four kinds of indirect evidence: synthetic long-context benchmarks, context-management ablations on SWE-bench-style tasks (mostly on non-Claude models), Anthropic's own qualitative statements, and practitioner anecdotes.

The thresholds that circulate in the community are judgment, not measurement. The "40-60% utilization" band comes from HumanLayer's 2025 workflow write-up for a 200K window, supported by case studies and described as depending "on complexity of the problem" ([HumanLayer](https://github.com/humanlayer/advanced-context-engineering-for-coding-agents/blob/main/ace-fca.md)). Geoffrey Huntley's "approximately 170k of context window" is a personal observation with no method given ([ghuntley.com](https://ghuntley.com/ralph/)). One much-cited set of fill-level bands (noticeable at 40-50%, rough at 80%+) is the model's own guess about itself in a GitHub issue ([claude-code #34685](https://github.com/anthropics/claude-code/issues/34685)). Practitioners working on 200K-era models independently cite absolute figures between roughly 80K and 170K tokens; that is agreement among anecdotes. User reports on the 1M window split cleanly: some say Opus 4.6 at 1M "seems barely more capable at around 20% than the previous model at 75%" ([claude-code #34685](https://github.com/anthropics/claude-code/issues/34685)), others report "I use 500k+ context on these on a daily basis" without trouble ([Hacker News](https://news.ycombinator.com/item?id=47367129)). Nearly all of this testimony dates from the Opus 4.6 and 4.7 era (March to May 2026).

## Frontier models pushed the cliff out by an order of magnitude

The 2025 research that made "context rot" a household term describes models two to three generations old. Chroma's July 2025 study tested 18 models, the newest Claude being Opus 4, and found every one less reliable as input grew even on trivial tasks; Claude's distinctive failure was abstaining, giving it the lowest hallucination rates and the largest gap between focused (about 300 tokens) and full (about 113K tokens) prompts ([Chroma](https://www.trychroma.com/research/context-rot)). NoLiMa, which removes literal keyword overlap between question and answer, showed **Claude 3.5 Sonnet falling from 87.5% to 29.8% by 32K tokens**, and 11 of 13 models scoring below half their baseline at that length ([NoLiMa](https://arxiv.org/html/2502.05167v3)). These results overstate what a late-2026 model does at the same token counts.

The 2026 data moves the curve outward. Anthropic reported Opus 4.6 at 76% on the 8-needle MRCR v2 test at 1M tokens against 18.5% for Sonnet 4.5, the largest single generational jump in the record ([Anthropic](https://www.anthropic.com/news/claude-opus-4-6)). On GraphWalks, a graph-traversal test, the Anthropic-run series shows the 256K-to-1M loss shrinking with each release. These figures reached the research notes through an aggregator that attributes them to Anthropic's system cards; they were not checked against the cards themselves, and Anthropic's definition of the 1M subset changed between cards without explanation.

| Model (2026) | BFS at 256K | BFS at 1M | Loss |
|---|---|---|---|
| Claude Opus 4.6 | 61.1% | 16.3% | 45 points |
| Claude Opus 4.7 | 76.9% | 40.3% | 37 points |
| Claude Opus 4.8 | 85.9% | 68.1% | 18 points |
| Claude Mythos 5 | 91.1% | 79.4% | 12 points |

Source: [Klu.ai GraphWalks summary](https://klu.ai/benchmarks/graphwalks).

Three cautions temper the trend. First, progress is not monotonic: OpenAI's published comparison puts **Opus 4.7 at 59.2% on MRCR v2 at 128K-256K and 32.2% at 512K-1M**, far below Opus 4.6, even though Opus 4.7 beats Opus 4.6 on GraphWalks ([OpenAI](https://openai.com/index/introducing-gpt-5-5/)). Second, for the models Claude Code runs by default today, the only numbers are a competitor's: Google's October 2026 report puts Opus 5.5 at 90.6% up to 128K and 66.8% in the 256K-1M range, and Fable 5.1 at 91.4% and 65.0%, with grader and settings unspecified ([Klu.ai](https://klu.ai/benchmarks/graphwalks)). Third, independent work still finds large effects at the far end: Opus 4.6, GPT 5.4 and Gemini 3.1, used as monitors, missed a subtly dangerous coding-agent action **2x to 30x more often** when it followed 800K tokens of benign activity than when shown alone ([Martin and Roger](https://arxiv.org/abs/2605.12366)).

## Content and absolute tokens drive the loss, not percent full

No experiment isolates percentage-of-window from absolute token count, but everything measured points to absolute length and content. In NoLiMa, the advertised window did not predict the usable one: Gemini 1.5 Pro with a 2M window had an effective length of 2K tokens, Claude 3.5 Sonnet with 200K had 4K, and GPT-4o with 128K had 8K ([NoLiMa](https://arxiv.org/html/2502.05167v3)). In 2026, models sharing a 1M window score anywhere from 32.2% to 74.0% in the same 512K-1M bin ([OpenAI](https://openai.com/index/introducing-gpt-5-5/)). A 1M-window model at 200K tokens is therefore not "20% full and safe" by construction; its reliability there depends on that model's own curve.

What the extra tokens contain matters more than their count. Chroma found that distractors and lower question-answer similarity both steepen the length curve ([Chroma](https://www.trychroma.com/research/context-rot)). A November 2026 study found that attention mass on the evidence explains 35-58% of the variance in retrieval loss while length explains at most 8%, and that neutral filler up to 32K tokens causes almost no loss while same-format conflicting statements collapse accuracy; this was shown only on models up to 3B parameters and is predictive, not causal ([Liu](https://arxiv.org/html/2611.04169v1)). A long coding session is the high-competition case: several versions of the same file, repeated tool outputs and abandoned plans all resemble the thing the model needs.

Task type sets the slope. Single-fact lookup stays near ceiling even at 1M, while multi-hop reasoning loses tens of points over the same span. The same model at the same length shows the gap directly: GPT-5.5 at 1M scores 58.5% on one-hop GraphWalks lookups and 45.4% on multi-hop traversal ([OpenAI](https://openai.com/index/introducing-gpt-5-5/)). Agentic coding resembles the hard cases, since it depends on which edit came last and on tracing dependencies across files, so needle-in-a-haystack scores say little about it.

## In coding agents, compaction loses more than a full window does

Controlled agent studies show that old history contributes little to benchmark scores. JetBrains' ablation on SWE-bench Verified found that keeping only the last ten tool observations matched or beat the full-history agent while roughly halving cost in four of five configurations; Gemini 2.5 Flash, with a 1M window, scored 32.8% raw and 35.6% masked. The exception, Gemini 2.5 Flash with thinking, lost 4 to 9 points under context management, and no Claude model was tested ([JetBrains](https://arxiv.org/html/2508.21433v3)). The one study that tested a 1M Claude model directly, an October 2026 paper using the OpenCode scaffold, found **Opus 4.6 scores essentially flat whether compaction fired at 160K or 380K tokens**, while a 400K-window model fell from about 0.60 to 0.38 when compacted early. It tested nothing above 380K, so the 400K-1M range remains unmeasured for agentic coding ([Salle et al.](https://arxiv.org/html/2610.31778v1)).

The same paper quantifies what scores hide. Across 44 real Claude Code sessions containing 269 user constraints, **19% were missing from the next compaction summary** (24.5% under a second judge); feature requirements were dropped 6.2% of the time, process instructions 35.9% and scope exclusions 36.8%. The loss compounds because each summary is built from the last: of three rules stated at the start of a task, an average of 0.92 were gone after the first compaction and 2.41 after the fifteenth. Opus 4.6 was the most robust model tested, dropping 0.51 of three rules per compaction against 1.76 for GPT-5.4 ([Salle et al.](https://arxiv.org/html/2610.31778v1)). A vendor study of production coding sessions found tracking of which files were touched to be the weakest dimension after compression, scoring 2.19 to 2.45 out of 5 across three compaction methods ([Factory](https://factory.com/news/evaluating-compression)).

A separate mechanism explains much of what users experience as a session "getting dumb", and it has nothing to do with fill. When a task is revealed across several turns instead of one, performance drops 39% on average; Claude 3.7 Sonnet kept about 66% of its single-turn score, and restating everything each turn recovered only 15-20% of the gap. The conversations were short, so the variable is drip-fed requirements and early wrong assumptions, not length ([Laban et al.](https://arxiv.org/html/2505.06120v1)). Raw trajectory length is a weak signal too: failed SWE-agent runs are about 18.5% longer than successful ones ([arXiv 2511.00197](https://arxiv.org/pdf/2511.00197)), but task difficulty and model identity explain most failures ([arXiv 2611.08285](https://arxiv.org/pdf/2611.08285)).

## Anthropic relaxed its guidance while keeping the warning

Anthropic's position has shifted from capacity to focus. Its September 2025 post described context as a finite "attention budget" in which recall decreases as tokens increase ([Anthropic](https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents)). By March 2026 it reported that Sonnet 4.5 "exhibited context anxiety strongly enough that compaction alone wasn't sufficient", wrapping up work early near its perceived limit, and that Opus 4.5 "largely removed that behavior on its own" ([Anthropic](https://www.anthropic.com/engineering/harness-design-long-running-apps)). The current Claude Code docs list "the context window is your main constraint, manage it aggressively" as outdated: most models have a 1M window, compaction runs on its own, and running out is rare, though "a focused context gets you better answers and costs less" ([Claude Code docs](https://code.claude.com/docs/en/best-practices)).

The warning survives elsewhere in Anthropic's own material. The API docs say "As token count grows, accuracy and recall degrade, a phenomenon known as context rot" ([Claude API docs](https://platform.claude.com/docs/en/build-with-claude/context-windows)). A Claude Code team post from April 2026 advises a new session for each new task and notes that, because of context rot, "the model is at its least intelligent point when compacting" ([Anthropic](https://claude.com/blog/using-claude-code-session-management-and-1m-context)). Anthropic publishes no token threshold at which degradation begins, and no measurement of task success with and without compaction.

The defaults matter because they are permissive. Native-1M models (Fable, Opus 4.7 and later, Sonnet 5 and later, Haiku 5.5) compact "at about 967K tokens by default", and an earlier trigger is opt-in through `/autocompact` with a 100K minimum ([Claude Code docs](https://code.claude.com/docs/en/model-config#default-auto-compact-thresholds)). After compaction the project-root CLAUDE.md, auto memory and the plan-mode plan are re-injected from disk, while nested CLAUDE.md files, path-scoped rules and hook-added context are summarized away, and "detailed instructions from early in the conversation may be lost" ([Claude Code docs](https://code.claude.com/docs/en/context-window)). Many 2025 reports of Claude "forgetting CLAUDE.md after compact" therefore describe a harness that has since changed.

## Conclusion

The useful mental model is no longer a fuel gauge. For current Claude models the evidence supports a gentle, content-dependent slope through the first few hundred thousand tokens, steeper losses on multi-step reasoning toward 1M, and a discrete, measurable loss each time the conversation is compacted. That reorders the practical priorities: where an instruction lives matters more than how full the window is. A rule in root CLAUDE.md or a plan file on disk is immune to the one failure that has actually been quantified in Claude Code sessions, while a rule typed into chat has roughly a one-in-three chance of disappearing at the next compaction if it is a process or scope instruction. Fresh sessions per task and state on disk are the practices that hold at 200K and at 1M without depending on any threshold being right.

What would change this picture is a fill-level study on the models Claude Code ships today. Until Anthropic or an independent group publishes success-versus-tokens data for Opus 5.5 or the Fable models in a real agent harness, especially between 400K and 1M, every specific number offered as "the point where Claude gets worse" is either a retrieval benchmark standing in for coding or someone's experience on an older model.
